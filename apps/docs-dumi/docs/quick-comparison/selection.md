- 市面上有哪些可选方案，各自擅长什么

## 问题域（先对齐你在解决什么）

Weave 更偏向“业务侧生成结构化场景 → 引擎负责布局与绘制”，典型需求画像：

- 画面以“布局驱动”为主：卡片、表格、报表、列表、图文混排（flex + clip + text）
- 高频更新要稳：希望用 Patch 表达“变了什么”，而不是每次重建整棵树
- 主线程要轻：浏览器侧希望把 layout/paint 挪到 Worker（OffscreenCanvas）
- 同一份逻辑要跨端复用：浏览器实时预览 + Node 离屏导出（PNG 等）

如果你的需求更偏“复杂交互编辑器”“大量矢量路径/滤镜”“GPU 大规模精灵/粒子”，Weave 不是第一选项。

## 市面方案分层（按思路而不是按库名）

| 方案类别                       | 代表/常见选择                     | 优势                                               | 代价/局限                                                                                   |
| ------------------------------ | --------------------------------- | -------------------------------------------------- | ------------------------------------------------------------------------------------------- |
| DOM/CSS/SVG（浏览器原生）      | React/Vue + DOM、SVG              | 生态成熟、可访问性/排版强、交互与事件模型完备      | 大量节点时性能瓶颈明显；跨端（Node/Worker）复用困难；渲染与布局高度绑在浏览器               |
| Canvas 2D 直接绘制（即时模式） | 原生 Canvas 2D                    | API 简单、依赖少、成本低                           | 自己维护状态/重绘/脏矩形/布局；跨帧增量与结构化更新难，代码容易变成“命令式泥团”             |
| Canvas retained-mode/场景树    | Konva / Fabric / Paper.js 等      | 有场景树/事件/部分布局能力，适合图形编辑、对象管理 | 布局系统通常不以 flex 为核心；跨端（Node/Worker）能力不一；类型与增量更新协议不一定贴合业务 |
| WebGL/2D 渲染引擎              | PixiJS（WebGL/Canvas fallback）等 | GPU 加速、擅长大规模精灵/动画/特效                 | 学习与管线成本高；文字排版、复杂布局通常要额外体系；离屏导出与一致性要额外工程              |
| Skia/跨端绘制栈                | CanvasKit/Skia 生态               | 高质量绘制能力、跨平台一致性强                     | 体积与集成成本高；业务侧布局/增量更新仍需自己搭；对 Worker/Node 的组合方式更重              |

Weave 的定位更接近：为“布局驱动的 2D 业务画面”提供一套可序列化、可跨线程、可跨端的协议与最小引擎管线（SceneNode + Patch + DisplayList）。

## Weave 的优势（相对上述方案）

- 数据与渲染解耦：SceneNode/Patch 是纯数据，可结构化克隆，天然适合主线程 ⇄ Worker
- 增量更新明确：Patch 把“变化”表达成操作集，便于高频更新与性能控制
- 布局能力开箱：布局由 Yoga 负责，业务侧只维护 `LayoutStyle` 与约束
- 跨端复用清晰：DisplayList 是“平台中立”的绘制指令，browser/node 只需要 `Context2DLike`
- 边界可控：模块拆分让你能独立替换 adapter、扩展节点类型、或换绘制后端

## Weave 的代价（你需要接受的现实）

- 能力覆盖不如成熟引擎：目前原语与绘制指令集合是“业务优先”的子集，不追求全量图形能力
- 生态与工具链需要自给：调试工具、可视化编辑、资源/滤镜/高级文本排版等都需要逐步补齐
- 交互事件不是核心：Weave 的强项是 layout/paint，交互状态管理更适合留在 UI 框架侧

## 为什么选 Weave（什么时候“值”）

当你的目标是：

- 把“布局 + 绘制”当成可演进的引擎能力，而不是散落在业务里的 canvas 命令
- 需要 Worker 把主线程压力压下去，同时又希望更新协议清晰可控
- 需要浏览器预览与 Node 导出尽量共用同一份场景与更新逻辑

这时 Weave 的“协议化 + 分层管线”会显著降低后续扩展与维护成本。

## 是否在造轮子（造了哪些，复用了哪些）

- 复用的“轮子”：Yoga（布局）、Canvas 2D（绘制能力）、Node canvas backend（离屏输出基础）
- 自己造的“必要部分”：可序列化的 SceneNode/Patch 协议、从布局结果到 DisplayList 的产出、DisplayList 的平台中立 replay、Worker/Node 的端到端拼装

换句话说：不是从零写一个“全能渲染引擎”，而是把业务最需要的那段链路（布局驱动的 2D 场景 + 增量更新 + 跨线程/跨端）抽成一套可维护、可验证、可演进的最小系统。
